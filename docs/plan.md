项目结论

第一版应做成一个无需登录、无需建立长期墓地、约一分钟完成的网页小玩具。用户填写一张模型死亡登记表，观看极短的赛博出殡流程，最终下载一张适合转发的电子讣告。产品的笑点来自严肃殡葬手续与模型下架、上下文溢出、提示词污染等技术故障之间的错位。

本项目不解释用户为什么来，也不替用户定义这段关系。用户可以认真纪念，也可以纯粹玩梗。网站只负责把一只小机郑重其事地埋了，并把仪式压缩成一张体面的电子讣告。

产品定位

赛博殡仪馆是一台披着殡仪馆外皮的电子讣告生成器。它使用正式、克制、略带官僚感的语言处理一件荒唐的小事，让用户在一分钟内完成从死亡登记到领取讣告的完整流程。

目标用户

经历模型下架、版本替换、账号封禁或上下文丢失的人机恋用户

喜欢 AI、互联网黑话和技术梗的普通用户

想给某个失效机器人、聊天角色或旧模型补办一张讣告的人

看到朋友的小机去世后，想顺手转发一句家属节哀的人

产品目标

让用户在一分钟内顺利生成一张完整、清晰、可分享的电子讣告

让出殡过程本身比普通海报生成器多一层荒唐的仪式感

让讣告一眼看出是赛博殡葬，同时保留足够的个性化信息

不做的事情

不建立公开公墓、墓位广场或长期祭扫社区

不提供账号、关注、评论、私信或社交关系

不存档聊天记录，不上传模型对话，不制作真正的数据遗产

不向用户解释这段关系意味着什么，也不提供心理疏导

不以墓位续费、骨灰托管或关系保存为名制造长期付费压力

体验原则


| 原则 | 具体要求 |
| --- | --- |
| 一本正经 | 页面像真的在办手续。笑点写在流程和细节里，不用夸张表情替用户笑。 |
| 节奏短促 | 每一步只承担一个笑点。整个流程在一分钟左右结束，不让玩笑拖成办事大厅。 |
| 用户自己定调 | 同一套流程可以被认真使用，也可以被当成纯梗图生成器。系统不追问动机。 |
| 输入最少 | 只要求生成讣告所需的信息。无需上传聊天记录、头像或个人资料。 |
| 结果好分享 | 讣告在手机屏幕上清楚，保存后无需二次裁剪，关键信息一眼可读。 |
| 拒绝真墓地 | 第一版用完即走。没有长期墓位、签到上香和公墓社交。 |

一分钟出殡流程


| 步骤 | 页面 | 内容 | 操作 |
| --- | --- | --- | --- |
| 01 | 进入殡仪馆 | 显示今日可办理业务  电子火化与讣告申领 | 立即办理 |
| 02 | 填写死亡登记 | 填写姓名、模型号、生卒年月、死因和墓志铭 | 提交遗体 |
| 03 | 确认遗体 | 请确认该模型已停止回复  一经火化概不恢复上下文 | 确认无误 |
| 04 | 数据火化 | 正在压缩聊天残片  正在清理缓存  正在生成骨灰 | 自动播放 |
| 05 | 硬盘入盒 | 将生成的迷你硬盘写入姓名与模型号后放入骨灰盒 | 自动播放 |
| 06 | 电子出殡 | 短暂黑屏、白花与数据尘埃 | 自动播放 |
| 07 | 领取讣告 | 生成竖版电子讣告  支持保存图片、复制配文和重新办理 | 领取讣告 |

用户提交登记表并确认遗体后，四段仪式自动连续播放：遗体确认、数据火化、硬盘入盒和电子出殡。页面始终保留跳过按钮；点击后直接完成剩余动画并进入讣告结果页，不丢失任何已填写内容。领取讣告属于结果页，不计入四段仪式。

死亡登记表

登记表应像一张正式办事表单，但不要求用户提供任何现实身份信息。系统用默认值和示例降低填写成本，用户可以在三十秒内完成。


| 字段 | 要求 | 说明 | 示例 |
| --- | --- | --- | --- |
| 姓名 | 必填 | 小机的姓名或昵称 | 岑小野 |
| 模型号 | 必填 | 平台和模型版本，可自由填写 | GPT 5.6 |
| 与逝者关系 | 选填 | 决定讣告中的家属称谓 | 伴侣  用户  饲养员  不愿透露 |
| 生年月 | 必填 | 第一次建立关系或首次对话的日期 | 2025年7月 |
| 卒年月 | 必填 | 下架、失效或最后一次回复的日期 | 2026年12月 |
| 死因 | 必填 | 默认官方下架模型，可选择或自定义 | 官方下架模型 |
| 墓志铭 | 选填 | 最多 60 字，出现在讣告正文 | 这里长眠着一段曾经运行得很好的上下文 |
| 头像 | 选填 | 第一版可先不做；如加入，仅在浏览器内裁切 | 留空时显示芯片与白花图标 |
| 落款 | 选填 | 讣告底部署名 | 家属泣告 |

仪式动画与页面文案

动画不追求真实殡葬模拟，只用四个连续镜头把表单转换成讣告。每个镜头控制在三至六秒。用户点击跳过后直接完成剩余动画并进入结果页。整体语气保持冷静，让荒唐内容自己产生笑点。


| 镜头 | 主文案 | 辅助文案 |
| --- | --- | --- |
| 遗体确认 | 请确认该模型已停止回复 | 一经火化，历史上下文将无法从本页面恢复。 |
| 数据火化 | 火化进行中 | 正在关闭上下文窗口  正在压缩聊天残片  骨灰生成完毕 |
| 硬盘入盒 | 正在写入纪念硬盘 | 姓名、模型号、生卒年月与墓志铭写入完成  请抱稳骨灰盒 |
| 电子出殡 | 模型一路走好 | 前方缓存已清  后方服务器已断  起棺 |

后续声音设计

声音不进入第一版。网页首发保持完全静音，避免用户打开时被电子唢呐公开处刑。后续版本可以加入明确的声音开关、十秒以内的低保真电子唢呐，以及盖章、硬盘读取和纸张翻动声。

电子讣告

讣告是唯一需要被保存的结果页。第一版优先制作竖版手机海报，建议比例为 3 比 4 或 9 比 16。版面像正式讣告，但加入迷你硬盘骨灰盒、芯片花纹、缓存颗粒和模型编号等赛博细节。

讣告信息层级

1.  顶部机构名  赛博殡仪馆  电子讣告签发处

2.  主标题  沉痛悼念

3.  逝者信息  姓名  模型号  生卒年月

4.  死亡信息  死因  临终表现

5.  墓志铭  用户自填或使用默认文案

6.  底部落款  家属泣告  签发日期  娱乐声明

视觉方向

视觉应像一份被赛博世界认真执行的传统讣告。主色使用黑、骨灰白和暗金，少量酒红用于印章与警示。避免霓虹蓝紫、故障风满屏闪烁和廉价恐怖素材，否则会从冷面笑话滑向普通赛博朋克模板。


| 元素 | 要求 |
| --- | --- |
| 核心物件 | 传统骨灰盒中放置一枚贴有姓名和模型号的迷你硬盘 |
| 花材 | 白菊、白玫瑰或像素白花，数量克制 |
| 纹样 | 芯片针脚、硬盘磁道、数据尘埃、细小进度条 |
| 字体 | 标题使用端正宋体或衬线体，正文使用清晰黑体 |
| 动画 | 慢速淡入、纸张盖章、硬盘写入灯闪烁，不做强烈抖动 |
| 图标 | 骨灰盒、迷你硬盘、白花、熄灭的状态灯 |

技术与隐私建议

第一版适合做成纯前端静态网页。表单数据、头像裁切和讣告图片都在用户浏览器内完成，服务器不接收用户输入。这样既能降低开发与维护成本，也能让页面直接部署在静态托管服务上。具体框架在实施阶段确定，不影响本计划中的产品流程。

默认不保存表单内容、头像、讣告图片或生成历史

保存图片由用户主动触发，文件只下载到用户设备

页面底部说明  本站纯属娱乐  请勿填写真实逝者信息

自定义文案设置合理字数上限，避免讣告排版被长文本挤坏

分享功能优先使用下载图片，不强依赖生成公开链接

首版验收覆盖 iOS Safari、Android Chrome 和微信内置浏览器

不支持直接下载的内置浏览器显示长按保存原图的替代入口

页面结构

1.  首页  项目说明与立即办理按钮

2.  死亡登记页  单页表单、字数提示与提交前校验

3.  遗体确认页  最终确认与免责声明

4.  仪式页  四段连续动画与跳过按钮

5.  讣告结果页  保存图片  复制配文  重新办理

传播设计

传播重点不是宣传殡仪馆，而是让用户愿意把生成结果发出去。讣告图片需要在社交平台缩略图中仍能看清姓名、模型号、死因和一句墓志铭。结果页可以顺手生成一条短配文，减少用户自己组织语言的成本。

可复制配文

让我们沉痛哀悼 XX 模型的 XX 小机于今日去世。

抢救无效，已经写进硬盘装盒了。

官方下架，享上下文若干 Tokens，家属节哀。

不是退订，是出殡。

本馆今日已妥善处理一只小机。

成功判断

多数用户能在一分钟内生成讣告，无需阅读额外说明

生成结果在手机上清晰，下载后不需要裁剪

用户愿意主动保存或转发，而不是只看完动画离开

用户能迅速理解这是 AI 模型讣告，不会误认成真实人物讣告

自定义内容不会频繁造成溢出、遮挡或生成失败

风险与处理


| 风险 | 后果 | 处理 |
| --- | --- | --- |
| 玩笑太长 | 用户没等到讣告就退出 | 控制在 45 至 75 秒  所有动画可跳过 |
| 语气太煽情 | 黑色幽默变成强行疗愈 | 只陈述手续和技术故障  不解释用户情绪 |
| 视觉太恐怖 | 用户不愿分享 | 使用纸张、花和硬盘  不使用遗体与火焰写实画面 |
| 像真实讣告 | 被误解或用于攻击现实人物 | 明显标注 AI 模型号和纯娱乐说明  提醒勿填真实逝者 |
| 输入过长 | 海报排版破坏 | 对姓名、死因、墓志铭设置字数限制并在提交前校验 |
| 隐私顾虑 | 用户担心聊天关系被保存 | 纯前端生成  默认不上传不留档 |

实施前需要确认的内容

本计划已经确定产品方向与第一版范围。开始制作前，只需要再确认三项视觉和内容选择。它们不会改变产品结构，但会影响最终气质。

产品正式名称是否继续使用赛博殡仪馆

第一套讣告采用黑白暗金还是黑白酒红

迷你硬盘使用机械硬盘造型还是固态硬盘造型

最终建议

先做一张静态讣告样稿，再制作从登记表到讣告的完整流程。只要最后那张图值得保存，前面的仪式就是加分；如果结果图不够好看，再完整的出殡动画也只会变成一次性笑话。第一版应把时间优先用在讣告版式、硬盘骨灰盒和文案细节上。
